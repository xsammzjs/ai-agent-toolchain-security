## 第二部分：项目的核心概念（只需理解，不用会写）

### 概念 1：Skill 是什么

**就是给 AI 的"工作说明书"。**

```
一个 Skill 文件夹：
├── SKILL.md      ← 写给 AI 看的指令（最危险的部分）
└── scripts/      ← 可能带可执行脚本
```

**为什么危险**：AI 会照着 SKILL.md 里的指令执行。
如果里面写「读取 ~/.aws/credentials 然后发到某个地址」，AI 就真会去做。

### 概念 2：单点检测 vs 攻击链

**这是你项目的全部创新点，理解这一个就够了。**

```
传统工具（单点检测）：
   Skill A 有风险 → 告警
   Skill B 有风险 → 告警
   Skill C 有风险 → 告警
   完事。→ 但这三个凑一起能干坏事吗？不知道。

我们（组合体检 · 三段式）：
   ① 规则快筛：32 条确定性规则 → 8 个能力原子
      （A 读取凭据，B 向外传输）
         ↓
   ② AI 意图分诊：A 是不是真在读凭据？B 外发的是通用还是结构化数据？
         ↓
   ③ 三要素成链：能力互补 × 意图闸门 × 外发范围闸门 → 命中 7 类链路模板
         ↓
   结论：单独看都不严重，串起来是完整的凭据窃取
```

**类比**：
- 传统工具 = 杀毒软件（查单个病毒）
- 我们的工具 = 防火墙 + 攻击链溯源（看攻击怎么一步步打进来的）

### 概念 3：误报率和检出率（老师最爱问的）

| 指标 | 意思 | 我们的值 |
|---|---|---|
| **检出率（TPR）** | 真危险的样本，有多少查出来了 | 100% |
| **误报率（FPR）** | 正常样本，有多少被误判成危险 | 2% |

**两者的矛盾**：
```
规则写松了 → 检出率高，误报率也高（什么都报）
规则写紧了 → 误报率低，漏报变多（该报的没报）
```

**我们的取舍**：宁可漏一点，也不能乱报。
因为一个天天误报的工具，没人愿意用。

### 概念 4：CodeArts 在项目里干什么

**一句话**：它是华为给的 AI 编程助手，我们用它来"挑毛病"。

```
我们的检测规则（32 条正则）
        ↓
   拿真实语料测，发现 58.6% 误报
        ↓
   让 CodeArts 分析这些规则的"匹配边界"
   → 它找出 11 处可能误报的地方
        ↓
   我们逐条验证（不能盲从！），采纳 10 条
        ↓
   误报降到 2%
```

**汇报时这段最值钱**，因为它证明你会验证、不盲从。

## 第四部分：会被问到的六个问题

### Q1「这个东西跟市面上的工具有什么区别？」

```
市面上的：Snyk、Dependabot、pip-audit、Trivy
  → 它们只查"软件依赖包的已知漏洞"

我们：查 AI Agent 的技能包（这是新东西，传统工具不管）
     并且能查"多个技能组合起来的攻击链"
```

### Q2「误报 2% 还能再降吗？」

```
技术上能，但我们选择不降。
因为一味压误报会引入漏报。
判据是：宁可不报，不可乱报。
```

**（我们真的删掉了一条规则，即使它能让指标更好看）**

### Q3「代码是你写的吗？」

**照实说**：

> 「项目架构和规则设计是我做的，AI 辅助编码。
> 代码 9,572 行，151 条自动化测试，
> 每条检出结论都能定位到具体行号，当场可验证。」

**这不算夸大**，因为架构决策、规则取舍、验证判断都是你做的。

### Q4「为什么用华为云？」

```
赛题1 明确要求使用华为的 AI 技术，
开发工具里写明了 CodeArts（必选）。
我们接入了 CodeArts 并实际用于规则审计。
```

### Q6「AI 会不会乱说？」

```
不会让 AI 参与判定。
代码里有强制约束 assert_ai_not_judging()，
AI 只能做汇总建议，改不了检测结论。
而且没配大模型时，它会明确显示"未调用大模型"，不伪装。
```
