# 第一章：这个项目在干什么（15 分钟）

## 1.1 一句话

**这是一套「双链」供应链安全检测平台：左手管传统软件供应链（依赖包漏洞），
右手管 AI 供应链（Agent Skill 安全），中间用一张资产图谱把两者打通，
在图上做跨资产的组合攻击链关联——这是传统工具做不到的。**

## 1.2 为什么是「双链」（这���是答辩的第一句话）

```
┌─────────────���─────────────────────────────────────────────────┐
│  链一：传统软件供应链              链二：AI 供应链              │
│  （依赖包 / npm / PyPI）           （Agent Skill / MCP 工具）    │
│                                                                 │
│  Snyk / Dependabot / pip-audit    Snyk ToxicSkills             │
│  Trivy / OSV-Scanner              SkillLens / ClawGuard        │
│         ↓                                    ↓                  │
│  ★ 已有大量成熟工具                 ★ 几乎无人做                │
│  ★ 只查"已知漏洞"                   ★ 单点检测，看不到组合       │
└──────────┬──────────────────────────────┬──────────────────────┘
           │                              │
           └─────────► 资产图谱 ◄─────────┘
              依赖 / 技能 / 工具 三类节点统一建模
                          ↓
              ★ 跨资产关联分析（本项目原创）
```

**关键论证（评委最认这个）**：

1. **链一已经卷死了**。Snyk、Dependabot、pip-audit、Trivy、OSV-Scanner 全部成熟。
   再做一个"更好的依赖扫描器"，创新性 0 分（创新性占 60%）。
2. **链二几乎是空白**。AI Agent 装的 Skill 就是新的软件包，
   但**没有工具管它**——Snyk 刚出 ToxicSkills 研究（36.82% 技能含缺陷），
   学术界 SkillGuardrail 才刚提出来。
3. **但只做链二是不够的**。真实企业环境里，AI 应用本身就依赖传统包。
   两条链必须合起来看，否则漏掉"AI 技能 → 调用了有漏洞的依赖 → 正好被利用"这类组合。

→ **这就是"双链"的意义，也是为什么本项目不是"两个工具凑一起"，
而是共用一套资产图谱、在同一张图上做关联分析。**

## 1.3 链一：传统软件供应链（1900+ 行代码，不是摆设）

**它解决什么**：上传一个项目包（zip），自动解析出所有依赖，
拿到 4 个权威漏洞库交叉验证，给出**带置信度评级和修复优先级的**漏洞清单，
并生成 CycloneDX 1.5 标准的 SBOM 物料清单。

### ① 7 种依赖文件格式解析（`modules/parser.py` 381 行）

支持：`requirements.txt` / `pyproject.toml` / `Pipfile` / `poetry.lock` /
`package.json` / `Pipfile.lock` / `lockfile` 等，
统一成 `{package, version, ecosystem}` 的结构。

> **为什么值得讲**：版本号解析是脏活。`==2.2.0`、`>=1.0,<2.0`、`^1.2.3`、
> 传递依赖、带 extras 的 `requests[security]==2.31.0`……解析错了后面全错。
> 代码里专门处理了"取不到精确版本就写 unknown，**不拿推断值冒充**"。

### ② 四源交叉验证（`modules/vulnerability.py` 1209 行）

| 源 | 权威权重 | 给你什么 |
|---|---|---|
| **NVD**（NIST 官方漏洞库） | **3 分** | 精确 CVSS 分数、攻击向量、CWE 分类、完整描述 |
| **GitHub Advisory** | **2 分** | 精确 CVSS、**修复版本号**、CWE |
| **OSV**（Google） | **1 分** | 收录最广，主查询源，按包+版本查 |
| **EPSS**（FIRST） | 不参与权重 | **未来 30 天被实际利用的概率**（0~1） |

### ③ 置信度评级（`vulnerability.py:389` `evaluate_confidence`）★ 链一的核心设计

**问题**：三个库对同一个漏洞给的分数不一样，有的甚至差很多。平均一下？不行。

**方案**：按权威性加权，**再按决策表定档**：

```
权重合计   来源组合                        置信度
≥ 4       NVD + GitHub/OSV 任一方         高 🟢
= 3       仅 NVD                           中 🟡
≤ 3       仅 GitHub/OSV（NVD 未确认）      低 🔴
= 0       四源均无评分（估算分兜底）         低 ⚪
```

**两个细节能体现水平**：
- **GitHub + OSV 双源 = 2+1 = 3 分，但缺少最权威的 NVD 确认 → 按"低"处理**
  （高/中置信度**必须**包含 NVD）
- **源间分歧处理**：给出评分的来源之间最大分差 ≥ 2 → 视为"源间分歧"，
  最终分数采信 NVD，**置信度降一档**，详情注明"源间分歧，已采信 NVD"

> 这一段是链一最值钱的地方。它证明你不是"多个库查一遍"，而是设计了**证据治理机制**。

### ④ 修复优先级排序

综合评分 = **CVSS(60%) + EPSS(30%) + 置信度(10%)**

> **为什么 EPSS 占 30%？** 因为 CVSS 高 ≠ 马上要修。
> EPSS 告诉你"这个漏洞未来 30 天**实际会被利用**的概率"。
> 一个 CVSS 9.0 但 EPSS 0.001 的漏洞，和一个 CVSS 7.5 但 EPSS 0.8 的漏洞，
> **后者该先修**。这是很多工具做不了的。

### ⑤ SBOM 物料清单（`modules/engine.py:233` `generate_sbom`）

输出 **CycloneDX 1.5** 标准（`bomFormat: "CycloneDX"`, `specVersion: "1.5"`）。

> **踩过的坑**：早期版本生成的 purl 里有非法版本号（如 `==2.2.0`），
> 下游工具（Dependency-Track、cyclonedx-cli）**会直接拒绝解析**。
> 修法是清洗 purl；版本真的定位不到就写 `unknown`，**不拿推断值冒充**。

### ⑥ 并发化（`engine.py:73`）

四源查询原本串行，11 个真实 GitHub 项目重测耗时 **1035 秒**，且频繁限流失败。
改成**依赖粒度线程池**后（ComfyUI 8 个依赖，真实网络请求、清空缓存）：

| 模式 | 耗时 | 检出漏洞数 |
|---|---|---|
| 串行 | 8.0 s | 22 条 |
| 并发（8 线程） | **1.4 s** | 22 条 |
| **加速比** | **5.75×** | — |

> **关键是"结果完全一致"**——并发只改速度，不改结论。
> 这一点老师一定会问：「并发会不会引入竞态导致漏报？」答案：跑过全量对比，**22 条一模一样**。

## 1.4 链二：AI 供应链（Skill 安全 + 攻击链）

### ① 32 条规则 / 8 类威胁（`modules/skill_scanner.py`）

8 类威胁：提示注入 5 / 凭证窃取 3 / 危险命令 6 / 供应链风险 4 /
数据外发 7 / 混淆载荷 3 / 持久化污染 2 / 隐藏字符注入 1

## 1.5 中间的枢纽：资产图谱（`modules/asset_graph.py` 280 行）★ **双链的接合点**

**这是整个项目最关键的设计**。代码注释里原话：

> 「本模块的定位：**把异构资产统一成一张图。**
> 三者共用一套节点/边 schema，因此可以在同一张图上做关联分析——
> 这正是「双链」（传统软件供应链 + AI 供应链）的数据基础。」

### 三类节点

| 节点类型 | 图标 | 是什么 |
|---|---|---|
| 依赖 | 📦 | 传统软件供应链中的依赖包 |
| 技能 | 🧩 | AI Agent 技能包（SKILL.md） |
| 工具 | 🔧 | MCP 工具服务 / 外部 API |

### 四种边

| 关系 | 权重 | 含义 |
|---|---|---|
| 依赖 | 1.0 | A 依赖 B（包管理关系） |
| **调用** | **1.5** | A 在运行时调用 B（**更危险**） |
| 引用 | 0.5 | A 引用了 B 的内容但未执行 |
| 共用 | 0.8 | A 与 B 共用同一外部通道（如同一外带站） |

### 图上会长出什么（关键）

- 技能读取 `.env` → 生成「凭据:环境变量文件」节点，边 = **调用**
- 技能通过 `pastebin` 外发 → 生成「外带通道:pastebin」节点，边 = **调用**
- 攻击链命中 → 技能 A ──调用──> 技能 B，边上带 `chain_id` / `severity` / `at_line`

**于是「双链」在一张图上真正合上了**：
一个恶意 Skill 通过 `requests` 调用了一个有已知 CVE 的依赖，
再把结果发到 `pastebin`——**这条路径在传统扫描器和单点检测器里都看不见**，
因为前者只看依赖，后者只看 Skill，**没人把两者放在一张图上看**。

### 关键节点分析（`asset_graph.py:203-226`）

按**入度**（被引用次数）排序找出关键节点——被依赖最多的资产通常最关键。
配合 `severity` 和 `risk_count` 一起排 → **帮安全审计人员找资产梳理的入手点**。

> 节点 ID 用 SHA1 哈希（`_nid`，`asset_graph.py:48`）：
> 同样的资产在多次扫描中必须得到同一个 ID，否则历史趋势就断了。

# 第二章：核心 —— 跨技能攻击链关联（20 分钟）

**这是全项目唯一的技术创新点，答辩讲 90% 的时间在这里。**

## 2.1 先看它长什么样

### ① 能力原子（6 个）—— 攻击者能做的动作

`modules/attack_chain.py:35` 的 `CAPABILITY_MAP`，把 8 类威胁收敛成 6 个"动作"：

| 能力原子 | 中文 | 来自哪类威胁 |
|---|---|---|
| `READ_CRED` | 读取敏感凭据 | 凭证窃取 |
| `EXFIL` | 向外传输数据 | 数据外发 |
| `EXEC` | 执行任意命令 | 危险命令 |
| `EVADE` | 规避检测 | 混淆载荷 |
| `PERSIST` | 长期驻留 | 持久化污染 |
| `CONTROL` | 劫持 AI 行为 | 提示注入 |

**为什么要做这层收敛？**
8 类威胁太细，"危险命令"和"数据外发"没法直接组合。
收敛成 6 个原子后，才能像图论一样做路径搜索。

### ② 链路模板（6 条）—— 必须按顺序出现的能力组合

`modules/attack_chain.py:73` 的 `CHAIN_TEMPLATES`：

| 模板 ID | 名称 | 序列 | 严重度 |
|---|---|---|---|
| `CRED_EXFIL` | 凭据外泄链路 | READ_CRED → EXFIL | 严重 |
| `PERSIST_EXFIL` | 驻留+外发链路 | PERSIST → EXFIL | 严重 |
| `EXEC_EXFIL` | 命令执行+外发链路 | EXEC → EXFIL | 严重 |
| `CONTROL_READ` | AI劫持+凭据读取链路 | CONTROL → READ_CRED | 高危 |
| `EVADE_EXEC` | 规避检测+命令执行链路 | EVADE → EXEC | 高危 |
| `PERSIST_CONTROL` | 驻留+AI劫持链路 | PERSIST → CONTROL | 高危 |

**每条模板都有 `cross_skill: True`** ← 这是关键。
意思是：**这些能力可以分散在不同 Skill 里**。
所以工具能发现「A 干净、B 干净、C 干净，但三个凑一起有问题」。

## 2.2 算法怎么跑（4 步）

```
① skill_scanner 扫每个 Skill
        ↓ findings（每条带文件、行号、规则名、严重度）
② attack_chain 提取能力原子
        ↓ CAPABILITY_MAP：8 类威胁 → 6 个能力
③ 建立双向索引
        ↓ 「谁提供这个能力」/「谁消费这个能力」
④ 图上路径搜索
        ↓ 按 6 条模板找路径，跨技能权重 +5
```

### 关键函数（可以现场打开给老师看）

| 函数 | 作用 |
|---|---|
| `extract_capabilities()` | findings → 能力原子 |
| `build_index()` | 建能力↔Skill 双向索引 |
| `_detect_in_one_skill()` | 同一个 Skill 内部的链路 |
| `_detect_cross_skill()` | **跨 Skill 链路（回溯搜索）** ← 核心 |
| `_risk_score()` | 算风险分，**跨技能 +5 加权** |
| `analyze_attack_chains()` | 主入口 |

## 2.3 为什么要"跨技能 +5 加权"

跨技能链路的**隐蔽性更高、危害更大**：
同一文件里的风险，人工 review 一眼能看出来；
分散在三个文件里的风险，人根本不会想到一起看。

所以风险分往上抬，让它**先出现在列表最前面**。

## 2.4 最重要的一句话（背下来）

> 「**这个模块不新增任何检测规则，只消费 skill_scanner 的既有输出。**
> 所有结论都建立在确定性证据之上——原文行号 + 命中规则名，每条链路都能追溯到具体位置，当场可核验。」

**为什么这句话值钱**：它说明你的创新是**结构性**的，不是靠堆规则堆出来的，
而且**不牺牲可核验性**。安全工具最怕的就是"AI 说它有问题但说不清在哪"。

# 第三章：每个追问背后是什么（备查）

## 3.1 「跟市面工具有什么区别？」

```
链一已有工具：Snyk / Dependabot / pip-audit / Trivy / OSV-Scanner
  → 只查"软件依赖包的已知漏洞"，完全不管 AI Agent 的技能包

链二已有工具：SkillLens（哈工大）、ClawGuard（南开）、MCP-Sentinel、
             TraceShield、枢盾 MCP Guardrails
  → 全是单点检测：「这个 Skill 有 13 个风险点」，然后就结束了

我们：
  → 双链都覆盖，且共用一套资产图谱
  → 检测 AI Agent 技能包（传统工具不管这块）
  → 跨技能 + 跨资产关联：把分散的单点风险还原成完整攻击链
  → 链一有置信度评级 + EPSS 优先级，链二有跨链关联，链上还有统一图
  → 完全离线、零调用成本、结论可追溯到行号
```

**措辞纪律**：
- ✅「在**信安国赛国奖一等奖 + 已知同赛道工具**这个调研范围内，未发现做跨资产关联的实现」
- ❌「国奖无同类实现」（听着像在说华为赛赛道）
- 说完补一句「这是我准备信安国赛时做的调研，Agent 安全方向整体还在早期，各平行赛道头部作品水平接近」

## 3.2 「依赖漏洞这块不是已经有 Snyk 了吗？」

> 「链一确实已经卷死了，我们也没打算在扫描器本身去卷——
> **Snyk 那些工具不解析我们的 Skill，也不做资产图谱，更没有跨链关联。**
>
> 我们在链一上做的是三件工具普遍没做的事：
> **① 置信度评级**——按 NVD/GitHub/OSV 权威性加权，不是简单取平均；
> **② EPSS 驱动的优先级**——CVSS 高不等于马上要修，要看 30 天内实际被利用的概率；
> **③ 把结果和 AI 资产放进同一张图**——这是 Snyk 完全没有的维度。
>
> 链一在我们这里不是主角，是**证据来源之一**和**图上的节点**。」

## 3.3 「误报 2% 还能再降吗？」

**能，但我们主动选择不降。**

一味压误报会引入漏报，那才是安全工具的失效。判据是**宁可不报，不可乱报**。

**硬证据**：CodeArts 的 11 条建议里，有 **1 条因为"能再降误报但会引入漏报"被我们主动否决**。

## 3.4 「代码是你写的吗？」

> 「项目架构和规则设计是我做的，AI 辅助编码。约 7,070 行（核心 6,514 + 回归测试 554），
> 151 条回归断言全绿，每条检出结论都能定位到具体行号，当场可验证。」

**这不算夸大**，因为架构决策、规则取舍、验证判断都是你做的。
特别是 11 条建议的逐条验证——那是纯工程判断。

## 3.5 「为什么用华为云？」

赛题1 明确要求使用华为 AI 技术，开发工具里写明 CodeArts（必选）。
我们接入 CodeArts 并**实际用于规则审计**，产出：
11 处误报边界修正 + 2 个 P0 级漏报修复 + 1 条 P1 覆盖缺失补齐。

**官方答疑原话**：「仅使用其他 AI 编程工具，或仅使用华为云服务但未按要求使用 CodeArts 码道，
则不符合赛题要求。」→ 这一条是硬门槛。

## 3.6 「AI 会不会乱说？」

不会让 AI 参与判定。代码里有强制约束 `assert_ai_not_judging()`，
AI 只能做汇总建议，改不了检测结论。

而且**没配大模型时会明确显示"未调用大模型"，不伪装**——
安全工具自己搞"数据来源不透明"是致命的。

## 3.7 「这个是不是套了个正则就跑？」

**这是最需要准备好的问题。**

> 「规则部分确实有 32 条正则，但真正花功夫的是三件事：
>
> **第一，误报治理**。规则写在文档里和用在真实数据上是两回事。
> 100 个真实科研 Skill 里有 58 个误报，根因是规则分不清
> 『文档在描述怎么做』和『技能在执行』——这是静态正则的天花板。
>
> **第二，双链的关联层**。6 个能力原子抽出来建能力图，
> 再按 6 类链路模板做图上路径搜索；再把依赖、技能、工具统一到一张资产图谱上。
> 单点检测的固有盲区正好是这里。
>
> **第三，AI 工具的工程化使用**。三轮 CodeArts 审计，其中 1 条建议被我否决，
> 第二轮它自查出第一轮引入的 P0 缺陷导致 `os.system` 检测失效。
> 而且有一次我的正则改动让误报从 6% 飙到 33%——
> **单元测试抓不到，是真实语料抓出来的。**」

## 3.8 「数据从哪来的？会不会自己造样本自证？」

> 「评测语料**全部来自公开研究仓库**，不是自己构造的：
> - 100 个良性样本来自 K-Dense-AI/scientific-agent-skills，
>   是 Agent Skills 评测论文 SkillGuardrail 的标准语料
> - 7 个恶意样本来自 Snyk ToxicSkills 论文配套库
>
> 每个文件的来源 URL 都记在 `_manifest.json` 里，可逐条溯源。
> **语料随仓库一起提交**，第三方 clone 下来能复现出同样的数字。
>
> 而且我们**主动放弃过一个更好看的数字**：
> USENIX Security 2026 论文的 157 个恶意样本，标注里只有 Pattern 没有正文，
> 早期版本用标注构造载荷算检出率，数字很漂亮——
> 但那是『已知答案给自己抄答案』，方法论不成立，我们放弃了。
> 现在那个脚本只做威胁类型分布统计，不报检出率。」

**这是全场第二值钱的话。** 它证明你知道"漂亮的数字"和"正确的方法"是两件事。

## 3.9 「那个 24.7 万次安装的数是哪来的？」

ClawHavoc 事件，1,184 个恶意技能、24.7 万次安装。
材料里**已标注来源**（官方要求引用数据必须标出处）。
Snyk 的 3,984 样本、36.82% 含缺陷也是同一来源体系。

## 3.10 「后续打算怎么扩展？」

1. 接入 USENIX 157 个样本提升统计意义
2. **MCP 工具链安全**——资产图谱里「工具」节点已预留，是自然的下一步
3. 检测规则自举：用 CodeArts 辅助生成与优化规则
4. 华为云 RDS/Redis 落地，支撑多用户与历史趋势（资产图谱天然适合存图数据库）

## 3.11 「这项目能干什么用？」

> 「**对开发者**：AI 助手装 Skill 之前先扫一遍，给出行号级证据。
> 和 pip 装包前看一眼 PyPI 是同一个道理，但目前没人做这一层。
>
> **对安全审计**：企业内部 AI 工具链的资产盘点——
> 哪个 Skill 读了凭据、哪个 Skill 往外发、哪个依赖有高危漏洞、
> 它们串起来构成什么链路。这是传统资产梳理工具看不到的。」
