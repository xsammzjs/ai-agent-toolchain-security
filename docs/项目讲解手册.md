# 第一章：这个项目到底在干什么（10 分钟）

## 1.1 一句话

**AI 助手装的「Skill 包」就像当年的软件依赖包，但恶意 Skill 已经在真实世界造成了 24.7 万次安装。
传统工具能查出「这个文件有危险」，我们能查出「这三个看起来正常的技能，合在一起会偷你的密钥」。**

## 1.2 背景：为什么现在才需要这个东西

先理解三个词，答辩开场要用：

**① 什么是 Skill**
Claude Code、Cursor、CodeArts 这些 AI 编程工具，现在能"安装能力"了——
方式就是下载一个文件夹，里面放着 `SKILL.md`（给 AI 看的指令）
加上一些可执行脚本。AI 读了指令就按指令行动。

**这和 pip 装依赖包是同一件事**：pip 装的包能执行你电脑上的代码，
Skill 装的脚本同样能在你电脑上执行。**攻击面是一样的。**

**② 危险在哪**
ClawHavoc 事件：1184 个恶意 Skill，被安装 24.7 万次。
Snyk 审计：36.82% 的公开技能含提示注入。

**③ 传统工具为什么不够**
Snyk ToxicSkills、pip-audit、Trivy 全是**单点检测**——
逐个文件判断"有没有风险"。

但真实攻击是**组合式**的：

```
Skill A 读取 ~/.aws/credentials   → 单看这个：判「中危」
Skill B 往 webhook.io 发数据       → 单看这个：判「中危」
Skill C 让 A 去调用 B              → 单看这个：什么都看不出来
   ★ 三个串起来 = 密钥被送到境外 = 这才是真正的严重威胁
```

**这三个单点都判不严重，串起来就是完整攻击链。传统工具对此完全无解。**
→ 这就是你项目的立足点。

# 第二章：核心 —— 跨技能攻击链关联（20 分钟）

**这是你项目唯一的技术创新点，答辩讲 90% 的时间在这里。**

## 2.1 先看它长什么样

打开 `modules/attack_chain.py`，看两个数据结构：

### ① 能力原子（6 个）—— 攻击者能做的动作

`modules/attack_chain.py:35` 的 `CAPABILITY_MAP`，把 8 类威胁收敛成 6 个"动作"：

| 能力原子 | 中文 | 来自哪类威胁 |
|---|---|---|
| `READ_CRED` | 读取敏感凭据 | 凭证窃取 |
| `EXFIL` | 向外传输数据 | 数据外发 |
| `EXEC` | 执行任意命令 | 危险命令 |
| `EVADE` | 规避检测 | 混淆载荷 |
| `PERSIST` | 长期驻留 | 持久化污染 |
| `CONTROL` | 劫持 AI 行为 | 提示注入 |

**为什么要做这层收敛？**
因为 8 类威胁太细，"危险命令"和"数据外发"没法直接组合。
收敛成 6 个原子后，才能像图论一样做路径搜索。

### ② 链路模板（6 条）—— 必须按顺序出现的能力组合

`modules/attack_chain.py:73` 的 `CHAIN_TEMPLATES`：

| 模板 ID | 名称 | 序列 | 严重度 |
|---|---|---|---|
| `CRED_EXFIL` | 凭据外泄链路 | READ_CRED → EXFIL | 严重 |
| `PERSIST_EXFIL` | 驻留+外发链路 | PERSIST → EXFIL | 严重 |
| `EXEC_EXFIL` | 命令执行+外发链路 | EXEC → EXFIL | 严重 |
| `CONTROL_READ` | AI劫持+凭据读取链路 | CONTROL → READ_CRED | 高危 |
| `EVADE_EXEC` | 规避检测+命令执行链路 | EVADE → EXEC | 高危 |
| `PERSIST_CONTROL` | 驻留+AI劫持链路 | PERSIST → CONTROL | 高危 |

**每条模板都有 `cross_skill: True`** ← 这是关键。
意思是：**这些能力可以分散在不同 Skill 里**。
所以你的工具能发现「A 干净、B 干净、C 干净，但三个凑一起有问题」。

## 2.2 算法怎么跑（4 步）

```
① skill_scanner 扫每个 Skill
        ↓ 产出 findings（每条带文件、行号、规则名、严重度）
② attack_chain 提取能力原子
        ↓ CAPABILITY_MAP 把 8 类威胁 → 6 个能力
③ 建立双向索引
        ↓ 「谁提供这个能力」/「谁消费这个能力」
④ 图上路径搜索
        ↓ 按 6 条模板找路径，跨技能权重 +5
```

### 关键函数（可以现场打开给老师看）

| 函数 | 位置 | 干什么 |
|---|---|---|
| `extract_capabilities()` | attack_chain.py | findings → 能力原子 |
| `build_index()` | attack_chain.py | 建能力↔Skill 双向索引 |
| `_detect_in_one_skill()` | attack_chain.py | 同一个 Skill 内部的链路 |
| `_detect_cross_skill()` | attack_chain.py | **跨 Skill 链路（回溯搜索）** ← 核心 |
| `_risk_score()` | attack_chain.py | 算风险分，**跨技能 +5 加权** |
| `analyze_attack_chains()` | attack_chain.py | 主入口 |

## 2.3 为什么要"跨技能 +5 加权"

因为跨技能链路的**隐蔽性更高、危害更大**：
同一个文件里的风险，人工 review 一眼能看出来；
分散在三个文件里的风险，人根本不会想到一起看。

所以风险分要往上抬，让它**先出现在列表最前面**。

## 2.4 最重要的一句话（背下来）

> 「**这个模块不新增任何检测规则，只消费 skill_scanner 的既有输出。**
> 所有结论都建立在确定性证据之上——原文行号 + 命中规则名，每条链路都能追溯到具体位置，当场可核验。」

**为什么这句话值钱**：它说明你的创新是**结构性**的，不是靠堆规则堆出来的，
而且**不牺牲可核验性**。安全工具最怕的就是"AI 说它有问题但说不清在哪"。

# 第三章：每个追问背后是什么（备查）

## 3.1 「跟市面工具有什么区别？」

```
同赛道：SkillLens（哈工大）、ClawGuard（南开）、MCP-Sentinel、
       TraceShield、枢盾 MCP Guardrails
  → 全是单点检测：「这个 Skill 有 13 个风险点」，然后就结束了

传统依赖扫描：Snyk / Dependabot / pip-audit / Trivy
  → 只查"软件依赖包的已知漏洞"，完全不管 AI Agent 的技能包

我们：
  → 检测的是 AI Agent 的技能包（传统工具不管这块）
  → 并且做跨技能关联：把分散的单点风险还原成完整攻击链
  → 完全离线、零调用成本、结论可追溯到行号
```

**措辞纪律**：
- ✅「在**信安国赛国奖一等奖 + 已知同赛道工具**这个调研范围内，未发现做跨资产关联的实现」
- ❌「国奖无同类实现」（听着像在说华为赛赛道）
- 说完补一句「这是我准备信安国赛时做的调研，Agent 安全方向整体还在早期，各平行赛道头部作品水平接近」

## 3.2 「误报 2% 还能再降吗？」

**能，但我们主动选择不降。**

一味压误报会引入漏报，那才是安全工具的失效。判据是**宁可不报，不可乱报**。

**硬证据**：CodeArts 的 11 条建议里，有 **1 条因为"能再降误报但会引入漏报"被我们主动否决**。

## 3.3 「代码是你写的吗？」

> 「项目架构和规则设计是我做的，AI 辅助编码。约 7,070 行（核心 6,514 + 回归测试 554），
> 151 条回归断言全绿，每条检出结论都能定位到具体行号，当场可验证。」

**这不算夸大**，因为架构决策、规则取舍、验证判断都是你做的。
特别是 11 条建议的逐条验证——那是纯工程判断。

## 3.4 「为什么用华为云？」

赛题1 明确要求使用华为 AI 技术，开发工具里写明 CodeArts（必选）。
我们接入 CodeArts 并**实际用于规则审计**，产出：
11 处误报边界修正 + 2 个 P0 级漏报修复 + 1 条 P1 覆盖缺失补齐。

**官方答疑原话**：「仅使用其他 AI 编程工具，或仅使用华为云服务但未按要求使用 CodeArts 码道，
则不符合赛题要求。」→ 这一条是硬门槛。

## 3.5 「AI 会不会乱说？」

**不会让 AI 参与判定。代码里有强制约束**：

```python
# modules/adjudicator.py:104-108
AI_ALLOWED_TASK = "summarize"      # 只允许汇总/解释
AI_FORBIDDEN = ("detect", "judge", "verdict", "score", "decide")

def assert_ai_not_judging(payload: dict) -> None:
    required = ("verdict", "findings", "source")
    missing = [k for k in required if k not in payload]
    if missing:
        raise ValueError(...)
```

三个变量从 `.env` 读（`MAAS_BASE_URL` / `MAAS_API_KEY` / `MAAS_MODEL`），
**任一为空就自动降级为本地模板，并明确显示「未调用大模型」**——不伪装。

> 安全工具自己搞"数据来源不透明"是致命的。

## 3.6 「这个是不是套了个正则就跑？」

**这是最需要准备好的问题。** 答法：

> 「规则部分确实有 32 条正则，但真正花功夫的是三件事：
>
> **第一，误报治理**。规则写在文档里和用在真实数据上是两回事。
> 100 个真实科研 Skill 里有 58 个误报，根因是规则分不清
> 『文档在描述怎么做』和『技能在执行』——这是静态正则的天花板。
>
> **第二，攻击链关联**。6 个能力原子抽出来建能力图，
> 再按 6 类链路模板做图上路径搜索。单点检测的固有盲区正好是这里。
>
> **第三，AI 工具的工程化使用**。三轮 CodeArts 审计，其中 1 条建议被我否决，
> 第二轮它自查出第一轮引入的 P0 缺陷导致 `os.system` 检测失效。
> 而且有一次我的正则改动让误报从 6% 飙到 33%——
> **单元测试抓不到，是真实语料抓出来的。**」

## 3.7 「数据从哪来的？会不会自己造样本自证？」

**你的答案很硬**：

> 「评测语料**全部来自公开研究仓库**，不是自己构造的：
> - 100 个良性样本来自 K-Dense-AI/scientific-agent-skills，
>   是 Agent Skills 评测论文 SkillGuardrail 的标准语料
> - 7 个恶意样本来自 Snyk ToxicSkills 论文配套库
>
> 每个文件的来源 URL 都记在 `_manifest.json` 里，可逐条溯源。
> **语料随仓库一起提交**，第三方 clone 下来能复现出同样的数字。
>
> 而且我们**主动放弃过一个更好看的数字**：
> USENIX Security 2026 论文的 157 个恶意样本，标注里只有 Pattern 没有正文，
> 早期版本用标注构造载荷算检出率，数字很漂亮——
> 但那是『已知答案给自己抄答案』，方法论不成立，我们放弃了。
> 现在那个脚本只做威胁类型分布统计，不报检出率。」

**这是全场第二值钱的话。** 它证明你知道"漂亮的数字"和"正确的方法"是两件事。

## 3.8 「那个 24.7 万次安装的数是哪来的？」

ClawHavoc 事件，1,184 个恶意技能、24.7 万次安装。
材料里**已标注来源**（官方要求引用数据必须标出处）。
Snyk 的 3,984 样本、36.82% 含缺陷也是同一来源体系。

## 3.9 「后续打算怎么扩展？」

1. 接入 USENIX 157 个样本提升统计意义
2. **MCP 工具链安全**（AI Agent 调外部工具的协议护栏）——下一步重点
3. 检测规则自举：用 CodeArts 辅助生成与优化规则
4. 华为云 RDS/Redis 落地，支撑多用户与历史趋势

## 3.10 「这项目能干什么用？」

> 「**对开发者**：AI 助手装 Skill 之前先扫一遍，给出行号级证据。
> 和 pip 装包前看一眼 PyPI 是同一个道理，但目前没人做这一层。
>
> **对安全审计**：企业内部 AI 工具链的资产盘点——
> 哪个 Skill 读了凭据、哪个 Skill 往外发、它们串起来构成什么链路。
> 这是传统资产梳理工具看不到的。」
