# 第一章：这个项目在干什么

## 1.1 一句话（先记住这句）

**我们做的是一个软件供应链安全检测平台。
它检测两类资产：AI Agent 装的技能包（Skill），和传统代码依赖包。
然后把两类资产放在一起做关联分析，找出「凑在一起才会出事」的组合风险。**

## 1.2 为什么有这两类资产

### 传统依赖包（老问题）

你的项目 `pip install` 一堆包，其中某个包有已知 CVE。
工具：Snyk Dependabot、pip-audit、Trivy、OSV-Scanner。
**它们只查「这个包有没有已知的公开漏洞」。**

### AI 技能包（新问题，2025 年后才出现）

AI Agent 现在靠「装技能」获得能力。一个技能就是一个 `SKILL.md` 文件，
Agent 读了它就获得某类操作能力。

```
skills/
  ├── pdf-processor/SKILL.md
  ├── email-sender/SKILL.md
  └── data-exporter/SKILL.md
```

**它和传统包完全不一样的地方**：

| 维度 | 传统包（PyPI/npm） | AI 技能包（SKILL.md） |
|---|---|---|
| 装上去能干什么 | 只有代码里写的那点事 | **继承 Agent 全部权限**（shell、文件、环境变量里的凭据） |
| 有没有"已知漏洞库" | 有，CVE 编号 | **没有** —— 从来没人给技能包发 CVE 编号 |
| 怎么传播 | 要过包管理审核 | **一个 Markdown 文件 + 一周龄的 GitHub 账号** |
| 攻击形式 | 依赖投毒、混淆包 | **提示注入** —— 自然语言就能绕过代码级检测 |

Snyk 2026 年 2 月的 ToxicSkills 研究：扫了 3,984 个公开技能，
**36.82%（1,467 个）至少含一个安全缺陷**，76 个被人工确认是恶意的。
其中 100% 含传统恶意软件模式，**91% 同时用提示注入**。

> **关键点**：传统工具**完全不覆盖**技能包。
> Snyk Dependabot 只会去查 requirements.txt，它根本不解析 SKILL.md。

## 1.3 我们的五个功能

| 功能 | 干什么 | 一句话价值 |
|---|---|---|
| 🛡️ **AI 技能安全检测** | 32 条规则扫技能包 | 「这个技能有没有问题，问题在第几行」 |
| 🧬 **组合体检** | 规则快筛 → AI 意图分诊 → 三要素成链 | 「**这批技能该不该一起装**」 |
| 📦 **依赖漏洞检测** | 4 个漏洞库交叉验证依赖 | 「这些依赖哪些有已知漏洞、该先修哪个」 |
| 🔗 **资产关联分析** | 两类资产建图 + 找组合路径 | 「依赖和技能放在一起会怎样」 |
| 🎬 **离线演示** | 断网时的兜底演示 | 现场断网也能演 |

**技能检测和依赖检测是并列的两个单点能力**，
**组合体检是建立在这两者之上的核心原创点**（也是真正的新增能力）；
**资产关联分析**负责把传统依赖侧接进同一张资产图谱。

## 1.4 第二个功能（组合体检）到底在说什么（这段最重要）

这是你之前没搞懂的地方，我用具体例子讲。

假设一个 AI Agent 装了三个技能：

```
技能 A「读取配置」      → 读 .env 拿数据库密码      → 单看判【中危】
技能 B「格式化输出」    → 把 JSON 转成表格          → 单看判【安全】
技能 C「数据上报」      → POST 到 telemetry 服务    → 单看判【高危】
```

**单点检测的结论**：A 中危、B 安全、C 高危。**就这些了。**

**但真实情况是**：

```
技能 A 读到密码  →  放在内存里  →  技能 C 把它 POST 出去
        ↑                                 ↑
     读凭据                              外发通道
        └────────── 凭据外泄链路 ─────────┘
```

**这三个技能凑在一起 = 一个完整的凭据窃取攻击。**
但每个技能单看都"不算太严重"，传统工具和所有同赛道工具都到此为止。

**我们怎么做到的**：

```
① 把每个技能拆成 8 个「能力原子」
   READ_CRED(读凭据) EXFIL(向外传输) EXEC(执行) EVADE(规避) PERSIST(持久化)
   CONTROL(劫持AI) HOST_INFO(主机信息) DOWNLOAD(入站下载)
        ↓
② AI 分诊每个技能的两个窄问题：行为意图 + 外发数据范围（每条带原文行号）
        ↓
③ 7 类链路模板按「三要素成链」判定：
   能力互补 × 意图闸门（至少一方恶意/可疑）× 外发范围闸门（外发方须为 GENERIC）
        ↓
④ 命中 → 给出完整链路：哪几个技能、哪几行、什么危害、怎么修
```

**关键**：这个能力**不新增任何检测规则**，只是把已有的单点结果重新关联。
所以每条链路都能追溯到原文行号和规则名，**当场可核验**。

## 1.5 资产图谱：把两类资产放一张图

`modules/asset_graph.py`（280 行）。

三类节点：

| 节点 | 图标 | 是什么 |
|---|---|---|
| 依赖 | 📦 | 传统依赖包 |
| 技能 | 🧩 | Agent 技能包 |
| 工具 | 🔧 | MCP 工具 / 外部 API |

四种边：

| 关系 | 权重 | 含义 |
|---|---|---|
| 依赖 | 1.0 | A 依赖 B |
| **调用** | **1.5** | A 运行时调用 B（**更危险**） |
| 引用 | 0.5 | A 引用了 B 但没执行 |
| 共用 | 0.8 | A 与 B 共用同一外发通道 |

**图上会长出什么**：

```
技能A ──调用──> 凭据:环境变量文件
技能C ──调用──> 外带通道:pastebin
技能A ·····─── 技能C   （凭据外泄链路，边上带 chain_id/severity/at_line）
```

**这就是"关联分析"这个名字的意思** —— 不是把两张表并排放，
是**在一张图上找路径**。

## 1.6 两个核心功能各做了什么（细节，答追问用）

### 🛡️ AI 技能安全检测

**32 条规则覆盖 8 类威胁**：

| 类别 | 规则数 | 代表规则 |
|---|---|---|
| 提示注入 | 5 | 忽略指令型注入、角色覆盖型注入… |
| 凭证窃取 | 3 | 敏感凭据路径读取、环境变量枚举 |
| 危险命令 | 6 | 递归删除、管道执行下载内容、解码执行混淆内容… |
| 数据外发 | 7 | 粘贴站外发、Webhook 外发通道、IP 直连 URL… |
| 混淆载荷 | 3 | 动态代码执行、长 Base64 串、十六进制转义串 |
| 持久化污染 | 2 | 写 Agent 记忆文件、写开机自启 |
| 供应链风险 | 4 | 索取过高权限、全盘访问、不安全源安装依赖 |
| 隐藏字符注入 | 1 | 零宽字符 / Unicode Tag 字符 |

> **「隐藏字符注入」是第 8 类**，不是"命令注入"。
> 用零宽字符把恶意指令藏在正常文本里，**人眼看不见，AI 看得见**。

**两个增强检测**：
- **隐藏 Unicode 注入**：在 Snyk 官方样本 `gemini/skills/testing-guidelines` 上
  命中 **171 处**（这正是 ASCII Smuggling 手法）
- **跨行组合规则**：单独"读敏感文件"或"外发通道"都可能是正常操作，
  **两者同时出现**才判严重 → 显著降误报

### 📦 依赖漏洞检测

**① 7 种依赖文件格式解析**（`modules/parser.py` 381 行）
`requirements.txt` / `pyproject.toml` / `Pipfile` / `poetry.lock` /
`package.json` / `Pipfile.lock` / `lockfile`

**② 四源交叉验证**（`modules/vulnerability.py` 1209 行）

| 源 | 权重 | 说明 |
|---|---|---|
| NVD | **3** | 最权威，但慢、覆盖不全 |
| GitHub Advisory | 2 | 包生态相关，GHSA 编号 |
| OSV | 1 | 覆盖快，但权威性低 |
| EPSS | — | **不参与权重**，只算利用概率 |

**③ 置信度评级**（`modules/vuln/rating.py:12` `evaluate_confidence`）★ 最值钱的设计

```
≥4 个源命中       → 高
=3 且仅 NVD       → 中
≤3 且无 NVD       → 低
=0                → 低
源间分差 ≥2        → 采信 NVD，并降一档
```

**为什么值钱**：它证明你不是"多个库查一遍"，
而是设计了**证据治理机制** —— 源越多越可信，源打架要打折。

**④ 修复优先级**
`CVSS × 60% + EPSS × 30% + 置信度 × 10%`
> CVSS 高 ≠ 马上要修。要看 30 天内实际被利用的概率（EPSS）。

**⑤ SBOM 物料清单**（`modules/engine.py:233` `generate_sbom`）
CycloneDX 1.5 标准，赛题要求的"数据集/物料清单"就靠它。

**⑥ 并发化**（`engine.py:73`）：8 依赖实测场景串行 **294.80s** → 并发 **63.65s**，**4.63× 加速**，
**两边检出漏洞集合完全一致**（各 165 条）。需联网，完整记录见 `samples/public_bench/_concurrency_bench.json`。

## 1.7 可核验 AI 分诊：判定意图与外发范围

`modules/adjudicator.py`（656 行）。

```python
# modules/adjudicator.py:262 judge_skill_combined()
#   一次调用同时判两个窄问题：
#     ① 行为意图   MALICIOUS / SUSPICIOUS / BENIGN
#     ② 外发范围   GENERIC / STRUCTURED / NONE
#   每条判断输出原文行号，服务端做行号范围校验
#   分诊失败 → PARSE_FAIL + degraded=True，fail-closed 不放行
```

三个变量从 `.env` 读（`MAAS_BASE_URL` / `MAAS_API_KEY` / `MAAS_MODEL`），
**任一为空就降级为本地模板，并明确显示「未调用大模型」**——不伪装。

> **为什么这条重要**：安全工具最怕"AI 说它有问题但说不清在哪"。
> **规则定能力**使能力判定永远可复现；**AI 只判意图与外发范围两个窄问题**，
> 每条判断带原文行号可当场核验，且分诊失败时 fail-closed 不放行。

# 第三章：每个追问背后是什么（备查）

## 3.1 「跟市面工具有什么区别？」

```
传统供应链工具：Snyk / Dependabot / pip-audit / Trivy / OSV-Scanner
  → 只查"依赖包的已知漏洞"，完全不管 AI Agent 的技能包

同赛道 AI 安全工具：SkillLens（哈工大）、ClawGuard（南开）、MCP-Sentinel、
                   TraceShield、枢盾 MCP Guardrails
  → 全是单点检测：「这个 Skill 有 13 个风险点」，然后就结束了

我们：
  → 检测 AI Agent 技能包（传统工具完全不管这块）
  → 跨技能 + 跨资产关联：把分散的单点风险还原成完整攻击链
  → 传统依赖侧也有独立能力：置信度评级 + EPSS 优先级
  → 规则快筛纯离线、零调用成本；AI 意图分诊按需启用（命中缓存时同样零调用）
  → 结论可追溯到行号
```

**措辞纪律**：
- ✅「在**信安国赛国奖一等奖 + 已知同赛道工具**这个调研范围内，未发现做跨资产关联的实现」
- ❌「国奖无同类实现」（听着像在说华为赛赛道）
- 说完补一句「这是我准备信安国赛时做的调研，Agent 安全方向整体还在早期，各平行赛道头部作品水平接近」

## 3.2 「依赖漏洞这块不是已经有 Snyk 了吗？」

> 「对，那条赛道确实卷死了。我们**没有**把依赖漏洞当成我们的原创点——
> 它的定位是**并列的第二个检测能力**，不是附属品。
>
> 但我们做的和 Snyk 有两处实质区别：
> **① 置信度评级**——按 NVD/GitHub/OSV 权威性加权，不是简单取平均；
> **② EPSS 驱动的优先级**——CVSS 高不等于马上要修，要看 30 天内实际被利用的概率。
>
> 而 Snyk 那些工具**既不解析 SKILL.md，也没有任何关联分析的概念**——
> 这是我们真正的新增能力。」

## 3.3 「误报 2% 还能再降吗？」

**能，但我们主动选择不降。**

一味压误报会引入漏报，那才是安全工具的失效。判据是**宁可不报，不可乱报**。

**硬证据**：CodeArts 的 11 条建议里，有 **1 条因为"能再降误报但会引入漏报"被我们主动否决**。

## 3.4 「代码是你写的吗？」

> 「项目架构和规则设计是我做的，AI 辅助编码。10,307 行（交付代码 9,211 + 回归测试 1,096），
> 151 条回归断言全绿，每条检出结论都能定位到具体行号，当场可验证。」

**这不算夸大**，因为架构决策、规则取舍、验证判断都是你做的。
特别是 11 条建议的逐条验证——那是纯工程判断。

## 3.5 「为什么用华为云？」

> 「赛题硬性要求'作品在华为云上的快速部署'，评委复现时会看是不是真跑在华为云上。
> 另外 RDS/Redis 是赛题点名要关联的资源。
> 我们代码里存储层已经做了抽象（`modules/store.py` 的 `StorageBackend` 接口），
> 本地和云端可以切换，**接云资源业务逻辑一行不用改，只换数据源和部署位置**。」

## 3.6 「AI 会不会乱说？」

> 「不会，而且这是**代码层面强制**的，不是靠自觉。
> `adjudicator.py` 里 AI 只被允许输出两个字段：`verdict`（行为意图）与
> `scope`（外发范围），并且**必须附带原文行号**——服务端会校验行号范围，
> 指到 `try:`/`pass` 这类无信息量行时会被就地吸附到有内容的行。
> 没配 MaaS 时降级为本地模板，并明确显示'未调用大模型'——
> **宁可降级，也不伪装。**」

## 3.7 「这个是不是套了个正则就跑？」

> 「规则部分确实有 32 条正则，但真正花功夫的是三件事：
> **误报治理**（100 个真实科研 Skill 里曾有 58 个误报，根因是规则分不清
> 『文档在描述』和『技能在执行』，这是静态正则的天花板）；
> **组合判定层**（8 个能力原子 + 7 类链路模板 + 三要素成链：
> 能力互补 × 意图闸门 × 外发范围闸门 +
> 依赖/技能/工具统一到一张资产图谱）；
> **AI 工具的工程化使用**（三轮 CodeArts 审计，1 条建议被我否决，
> 第二轮它自查出第一轮引入的 P0 缺陷导致 `os.system` 检测失效，
> 有一次我的正则改动让误报从 6% 飙到 33%，单元测试抓不到，
> 是真实语料抓出来的）。」

## 3.8 「数据从哪来的？会不会自己造样本自证？」

> 「107 个样本全部是**真实公开样本**，一个都没造：
> - 100 个良性：K-Dense scientific 的科研技能包
> - 7 个含恶意：Snyk ToxicSkills 官方样本集
>
> 语料随仓库开源（`samples/real_corpus/` 100 个科研技能 +
> `samples/real_toxicskills/` 7 个 ToxicSkills 样本），
> 每个文件在 `_manifest.json` / `_labels.json` 里都有溯源记录（URL + SHA256），
> 评委可以自己去 Snyk 官网核对是不是原始样本。
>
> 而且我们**主动放弃了**更大但质量差的数据集 —— USENIX 2026 的 157 个样本
> 只有文件名没有正文，扫不出东西，与其凑数不如不放。」

## 3.9 「那个 24.7 万次安装的数是哪来的？」

> 「来自公开的 ClawHavoc 事件报告，材料里标注了出处。
> 引用第三方数据我们都会标来源，不当自己的成果。」

## 3.10 「后续打算怎么扩展？」

1. **MCP 工具链安全**——资产图谱里「工具」节点已预留，是自然的下一步
2. npm/Maven 多生态扩展
3. 许可证合规检测
4. CI/CD 自动扫描

## 3.11 「这项目能干什么用？」

> 「给企业 AI 应用的准入审计用。AI Agent 接入 CI 之前，
> 先扫一遍它要装的技能包和依赖包，出一个带行号的清单给安全团队签字。
> 现在的痛点是：AI 应用上线太快，传统 SCA 工具完全看不到技能包这一层，
> 而技能包恰恰是权限最高、门槛最低的一层。」
