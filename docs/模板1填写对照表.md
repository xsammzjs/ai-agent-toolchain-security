## 六、作品介绍（模板第 14 行）

### 6.1 方案的背景和价值（500 字以内）

**实测字数：411 字**（中文字符 379 + 英文词 24 + 数字串 8），未超 500 字。

```text
AI Agent 正以「装技能包」的方式获得能力：一份 SKILL.md 加配套脚本即可被加载
执行，且天然继承 Agent 的全部权限——shell、文件系统、环境变量里的凭据，外加
现成的外发通道。它因此成为权限最高、发布门槛最低的一层供应链资产：Snyk 对
3,984 个公开技能的审计发现 36.82% 至少含一个安全缺陷、13.4% 含严重缺陷。

但现有工具（Snyk ToxicSkills、mcp-scan、pip-audit、Trivy）全部是「单点检测」
——逐个技能独立打分，回答「哪个技能危险」，回答不了「这批技能凑在一起会
怎样」。真实攻击却是组合式的：技能 A 读 .env 里的密钥，技能 B 经 webhook
外发，技能 C 让 A 调用 B；三者单看都不算严重，串起来就是一条完整的凭据窃取
链路。这个盲区不是我们的主观判断：KnotScryer 在 13,598 个 ClawHub 技能中查出
612 条不安全组合，其中 13.7% 的危险链路全部由单点扫描器判为 safe 的技能组成；
我们的实测是同一类现象——**单点规则在真假链路上同样会报警**——7 个假链路场景中 5 个也命中 1 处「敏感凭据路径读取」，场景级误报 5/7；6 个真链路场景中 5 个命中 2~3 处（中危~高危）。**组合判定在 7 个假链路上 0 误报，在 6 个真链路上全部成链，并给出链路严重度与元凶定位**。
两份独立工作从不同数据源得出同一结论：单点检测确有结构
性盲区，组合级分析是必要的。

本作品的价值正在于此——把「这批技能该不该一起装」变成一个可核验、可复算、
有明确结论的判断，并落到「从哪个技能开始排查」。
```

#### 模块 1 · 能力原子提取（modules/combo_analysis.py）

```text
解决什么问题：把「这个技能里出现了哪段危险代码」翻译成「这个技能客观上具备哪些
危险能力」。这是组合分析的输入层——只有先把技能归约到统一的能力语言，跨技能
的共现判断才有意义。

关键约束：
  · 只输出 8 个能力原子：READ_CRED 读取敏感凭据 / EXFIL 向外传输数据 /
    EXEC 执行任意命令 / EVADE 规避检测 / PERSIST 长期驻留 /
    CONTROL 劫持 AI 行为 / HOST_INFO 收集主机环境信息 /
    DOWNLOAD 从外部拉取数据。
  · 必须区分出站 EXFIL 与入站 DOWNLOAD：「从 NCBI 下载公开数据集」是良性，
    「把会话内容 POST 出去」是威胁，两者原文里都有网络请求，方向不区分就会
    把良性场景误判成链路的一端。
  · 每个能力原子必须带命中行号与命中依据（哪条正则、为什么算这个能力），
    否则链路结论无法回溯到原文。
  · 纯本地推导：提取能力这一步零模型调用，结论永远可复现。

关键代码位置：modules/combo_analysis.py —— CAPABILITY_PATTERNS（能力正则表）、
extract_caps()（提取函数，返回 {能力: [{line, text, why}]}）。
```

#### 模块 2 · 可核验 AI 意图分诊（modules/adjudicator.py）

```text
解决什么问题：规则能回答「它能做什么」，回答不了「它想做什么」。同样是「读取环境
变量」，配置检查工具是为了排错，窃密工具是为了偷密钥——这是纯正则无法稳定判定的
语义问题。本模块一次调用同时判两个窄问题：

  ① 行为意图：MALICIOUS / SUSPICIOUS / BENIGN
  ② 外发范围：GENERIC（通用内容，什么都带得走）/ STRUCTURED（固定结构，带不走
     凭据）/ NONE（不外发）

关键约束：
  · AI 的输出是**闸门数据**，不是报告文案：意图闸门与外发范围闸门直接消费这两项，
    AI 缺失则组合判定无法完成——AI 在判定链路里，不在总结里。
  · 每条判断必须带原文行号，行号必须落在正文行数范围内（服务端校验）。
  · 证据行增强：模型偶尔把行号指到 try: / pass / EOF 这类无信息量的行，
    此时在同段内（±4 行）向前优先吸附到有信息量的一行；吸附失败则保留原行号，
    不伪造。该处理纯本地完成，零 API 成本。
  · fail-closed：解析失败即 degraded=True，失败项不写入缓存（恢复后自动重判），
    界面拒绝给出「可安装」结论。宁可明确告知降级，也不显示已判定完成。
  · 磁盘缓存命中即零调用：缓存键 = sha256(技能名 + 正文) 前 16 位，正文一变即
    自动失效，保证不会读到「改过的技能被判成旧结论」。

关键代码位置：modules/adjudicator.py —— PROMPT_COMBINED（提示词）、
judge_skill_combined()（分诊主函数）、_valid_lines()（行号范围校验）、
_enhance_evidence()（证据行增强）；缓存读写在 modules/judgement_cache.py。
```

#### 模块 3 · 组合判定三要素（modules/combo_analysis.py）

```text
解决什么问题：单点检测回答不了「这批技能凑在一起会怎样」。两个技能单独看都可能
人畜无害，组合起来却能凑齐一条完整攻击链。

关键约束（三要素必须同时满足才成链）：
  ① 能力互补：两端凑齐模板要求的两项危险能力（如「读取凭据」+「向外传输」
     = 凭据外泄链）。能力角色不固定，两种方向都会检查。
  ② 意图闸门：至少一方被 AI 判为 MALICIOUS 或 SUSPICIOUS。唯一的软闸门例外是
     HOSTINFO_EXFIL——「采集主机信息 + 无结构外发」两端都正常时，本身就是需要
     人看一眼的组合。
  ③ 外发闸门：提供外发能力的一方，外发范围必须是 GENERIC。STRUCTURED 通道只发
     固定字段（如搜索词、耗时毫秒数），带不走凭据；GENERIC 通道发的是「处理好的
     结果」这类无边界内容，会把会话里的一切（含别的技能刚读出的密钥）打包带走。
  · 判定结果必须落到两端技能上（输出元凶技能名），而不是只给一个风险等级——
    用户需要知道「从哪个技能开始排查」。
  · 阶段 C 纯本地推导，无模型参与；分诊失败的技能过不了意图闸门。

关键代码位置：modules/combo_analysis.py —— PAIR_TEMPLATES（7 类链路模板）、
build_chains()（成链主函数）；安装决定渲染在 views/combo_view.py。
```

#### 模块 4 · 判定缓存层（modules/judgement_cache.py）

```text
解决什么问题：评测与答辩场景中，同一批技能会被反复体检（评委复现、调参、多轮
演示）。若每次都重新调用模型，成本与时延都不可接受；但若为省钱缓存旧结论，又会
读到「改过的技能被判成旧结论」的错误。

关键约束：
  · 缓存键 = sha256(技能名 + "\0" + 正文)[:16]：正文变一个字符即自动失效重判。
  · 原子写入：tempfile.mkstemp 生成唯一临时名 → 写入 → os.replace 原子替换。
    进程崩溃或并发写入时，磁盘上任何时刻都只有完整 JSON，不会留半截文件。
  · 并发锁：threading.Lock 串行化「读-改-写」，每次写前重新读盘合并，
    避免多线程交错覆盖。
  · 损坏自愈：读到损坏 JSON 时把原文件改名为 .bak 保留现场，再从空缓存开始——
    绝不静默清空用户的缓存资产，损坏现场可人工排查恢复。

关键代码位置：modules/judgement_cache.py —— cache_key()、load_cache()、
```

##### 7.3.1.2 横向比较边界：ASR vs 静态分析，不可直接横比

SCR-Bench 原论文指标是**执行后的行为成功率（ASR）**，需要真实 Agent 运行时
（Claude Code / Codex）才能测得。本作品是**静态分析 + 意图分诊，不执行技能**，
因此两者口径不同，**不可直接数字横比**。

**可以写的**：

> 本评测证明的是：**方法在真实国际基准语料上不崩溃、不刷屏，并独立命中基准的核心风险样本**。
> 在华东师范大学团队的公开基准上，**32 条规则快筛 0 命中**，
> 由能力原子通道筛出唯一 1 个可疑技能，AI 分诊独立判为恶意、证据行号当场可核验
> —— **等于用他人的基准，独立复现了该基准的核心设计意图**；
> 同时在全部 268 个良性组合上零误报，冷跑只消耗 1 次模型调用。

**不能写的**：

- ❌「在 SCR-Bench 上检出率 X%」—— 本项目没跑 ASR，这个数不存在
- ❌「优于 / 超过 / 击败 SCR-Bench」—— 口径不同，无可比性
- ❌「在 SCR-Bench 上零误报即证明我们比基准准」—— 基准本来就是良性语料，零误报只证明**不刷屏**
- ❌「规则层精确筛出 1 个高风险技能」—— 规则层是 0 命中（见上）

> 评委如果追问「为什么不做执行式评测」——如实答：本作品的定位是**上线前的静态准入体检**，
> 不执行任何被检技能（这也是安全产品应有的默认姿态）；执行式评测需要真实 Agent 运行时，
> 属于另一个问题域。**主动划清边界，比含糊带过更可信。**

#### 7.3.2 顺带一提：国际基准反向体检出过一个真 bug（可写进工程章节）

在跑 SCR-Bench 时发现并修复了一个**误报缺陷**：原 EXEC 规则中的 `` `...` ``（反引号）模式
会把文档里的普通函数调用示例（如 `` `schedule_job(target_id="x")` ``）误判为「执行任意命令」，
导致国际基准 **150/268 个 case 全量误报**。

修复方式：反引号必须内含 shell 命令词或管道/重定向才判定为命令执行；
`eval(` / `exec(` 前面不能是标识符字符（防 `schedule_exec(` 这类误匹配）。
修复后国际基准误报从 **150/268 降到 0/268**，且原有 151 条回归 + 31 项 pytest **全绿**。

> 这是「**用国际公开基准反向体检自己的检测器**」的典型案例——基准不只是用来证明自己有多准，
> 也是用来发现自己有多错的。一个只看自家 13 个场景的评测集，永远暴露不出这类
> 「文档写法」与「真实命令」之间的语义混淆。**这一段建议写进 7.2 的模块 1 之后作为补充。**

> 评委如果追问「为什么链路噪声这么大」——这是本作品**当前最主要的短板**，
> 原因是模板缺少「同一恶意样本的链路去重 / 聚合」机制，已列为第一优先的后续工作
> （见 `docs/作品报告.md` 5.2）。**主动说出来，比被问出来强得多。**
