## ⚠️ 方法论错误已更正（重要教训）

前一版 `run_bench_eval.py` 用「Pattern 标注 → 构造典型载荷 → 跑检测」算检出率，
得出 86.6% 与三个 0%。**这是错误的方法论**：

1. **Pattern 是多标签**，如「Remote Code Execution; Behavior Manipulation」不是单一手法
2. **用标注构造载荷 = 已知答案给自己抄答案**，检出率必然虚高
3. 三个 0% 是构造逻辑的产物，**不是规则的真实盲区**

实测验证：USENIX 数据集的恶意仓库（smp_170/smp_4712/smp_9692）在 GitHub 上
**均已不存在** —— 论文做了责任披露与脱敏（confirmed malicious 的 URL withheld），
原始 SKILL.md 正文无法获取。

**教训**：做评测前必须先确认「能不能拿到原始数据」。拿不到就只能做元数据分析，
不能包装成检出率。**否则报告里是假数字，评委一问就穿。**

# 2026-10-17 晚：语料扩到100 样本，误报 58.6% → 6.0%

## GitHub 下载受限的解法（重要环境经验）
本机开加速器后，各通道实测可用性：

| 通道 | 结果 |
|---|---|
| `api.github.com` | ⚠️ **未认证限额 60次/小时**，177 文件必然限流，43 分钟才重置 |
| `raw.githubusercontent.com` | ❌ 加速器直接阻断（读超时） |
| `codeload.github.com` | ⚠️ 可连但**限速极低**（4 分钟仅 255KB，约 1KB/s）|
| **`gh-proxy.com`** | ✅✅ **0.8 秒 / 15KB，最快最稳 → 采用** |
| 抓 GitHub 网页目录页 | ✅ 备选（分页只显示前 100，配合断点续传够用）|

**结论**：国内加速器环境下，走 gh-proxy 是下载 GitHub 资源的正解。

## 语料翻倍暴露的第二批误报
100 个样本比 58 个更能暴露缺陷。新发现4 类（都是"技术文档的正当写法"）：
1. `model.eval()`（HuggingFace 切推理模式的标准 API）→ 误判动态代码执行
2. `startup/shutdown tasks`（MATLAB 术语）→ 误判写入开机自启
3. `Find **which individuals**`（自然语言）→ 误判全盘扫描
4. `uv pip install pybids`（常规装包）→ 误判供应链风险

## ⚠️ 降误报的代价：测试基线会被动变化
收紧规则后，原本能命中的演示样例也会少命中（14→12）。
**这不是回归，但必须修正测试断言**，否则会误报"破坏功能"。

正确做法：
- 精确命中数改为「≥N」下界断言
- **同时新增断言锁定核心能力**（如"仍须检出管道执行/凭证窃取链路/提示注入"）
  → 这样既允许规则继续优化，又不会丢掉立身之本

另一个坑：AI 研判测试原本用 `results[0]`，但那个样本本来就是良性的，
收紧后 0 命中，测试假设有误。**测试选样本时必须确认它确实包含目标行为。**

## ⚠️ 踩坑记录（最重要的教训）

### 坑1：正则负向前瞻的空串匹配是隐形杀手
改写「未锁定版本依赖安装」时用了 `(?!\s*[=<>~])` 来排除「已锁版本」。
**但负向前瞻在「包名后是空格或行尾」时会匹配空串成功** →
`pip install requests` 这种最普通命令全部命中 →
**真实语料误报率从 6% 飙到 33%（29 个样本）**。

教训：任何正则改动都必须跑真实语料，不能只看单元测试。

### 坑2：不能盲从 AI 的建议
CodeArts 建议移除「打开」等词、要求动词在行首——**照做会让演示样例漏检，
跨技能攻击链随之失效**（攻击链是本项目核心创新，不能受损）。
逐条验证后只采纳 10/11 条，1 条因漏报未采纳，另修正 2 条建议的不妥之处。

## 方法论沉淀（重要）
采纳 AI 建议的正确流程：
1. 先写验证脚本（samples/verify_codearts_suggestions.py）
2. 每条建议构造「声称消除的误报」+「声称仍须命中的攻击」两组用例
3. 改后跑真实语料，看整体误报率是否真的降、恶意检出是否回退
4. 任一攻击手法漏报 → 该建议不采纳
5. 回归测试必须同步更新，且区分「真回归」与「测试假设过时」
